Build a Python (Streamlit + pytest) month-end payments reconciliation tool.

1. Generator (seed 2026, Decimal only, no floats): October 2026 IST, 500 sales and 20 valid refunds on a platform file (3dp amounts) and a bank file (2dp, settlement 1-2 days later, running to 3 Nov, so some 30-31 Oct items settle in November). Plant exactly: timing items (all Oct items settling in Nov, including 1 refund), 60 rounding lines (+0.005 each on the platform, total 0.300), 1 duplicate platform row, 1 bank-only refund whose original is not in the platform data. Include two same-amount decoy sales and first/last-moment-of-month sales, and keep them out of all special sets. Self-assert all constraints before writing. Output platform.csv, bank.csv, ground_truth.csv, expected_totals.json.
2. Reconciler: dedupe-detect first, match txn_id = reference, classify exact / rounding (<= 0.005) / amount mismatch / timing / orphan refund (check every refund's original against the platform) / unexplained, give each a plain-language reason. Bridge: platform Oct total - bank Oct total = timing + rounding + duplicate + orphan + remainder, with an integrity check on the remainder. It never reads ground_truth or expected_totals. Each row must belong to at most one gap, so the orphan refund is flagged once and never counted twice.
3. Streamlit page: summary, bridge, gaps-by-type table, filterable detail table, assumptions.
4. Tests: detection vs ground truth, 0.300 rounding total, bridge vs expected totals with remainder 0, decoys not duplicates, month-boundary rows, a 0.005 / 0.006 tolerance edge, an unplanted-anomaly test (+10.00 and a deleted bank row make the remainder non-zero and flag the rows), a clean-data test, and a source-independence test.
Keep it simple and don't add features. Add a README with assumptions and 3 sentences on production risks.
